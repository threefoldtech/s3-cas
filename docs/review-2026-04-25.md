# State of the repo -- 2026-04-25 review

This document is a narrative snapshot of where `s3-cas` is on the
development branch as of 2026-04-25, what each recent PRD and ADR
actually means in practice, and what is actively on the table for
the next work session. It is meant to be read top-to-bottom; it
replaces the need to chase through the individual PRDs/ADRs just
to get oriented.

It is not an ADR or a PRD. It will not be updated as the project
evolves. If you are reading this after 2026-05 and something has
changed, trust the actual docs under `docs/adr/` and `docs/prd/`
over this narrative.

## 1. What the repo is, in one paragraph

`s3-cas` is an S3-compatible server with content-addressable
storage underneath: objects get chunked into 1 MiB MD5-hashed
blocks, blocks are deduplicated globally via reference counting,
and per-user metadata sits on top. The storage core lives in
`cas-storage` as a reusable library; `s3-cas` is the S3 protocol
adapter on top. The server is multi-user only (the single-user
mode was deleted in the simplify pass); there is no HTTP UI
anymore. Users are managed via `s3-cas user add|list|delete`,
each getting their own S3 access/secret key pair. Server runs on
one port; Prometheus metrics on another.

## 2. What PRD-000 was really about

PRD-000 is the anchor document. It does three things:

- Freezes "what exists today" (as of 2026-04-24) so later work
  can reference a stable baseline.
- Names the structural pain points that had accreted -- dual
  `CasFS` shapes, stale dep surface, a UI that wasn't really
  wanted, `rusoto_core` leaking into the library, dead
  documentation referring to deleted features.
- Proposes a target shape, not a rewrite.

Everything in the "Active PRDs" list under PRD-000 is a
decomposition of that target shape. They are subtractive and
mechanical where possible; none of them change the refcount
logic, transaction boundaries, chunk size, or hash algorithm.
Those are load-bearing and sacred.

## 3. What the recent PRDs did

### PRD-001 -- cas-storage internal restructure (done)

1198-line `cas/fs.rs` was doing five jobs in one file. Split into
`buckets.rs`, `read_path.rs`, `delete_path.rs`, `write_path.rs`,
`async_fs.rs`, and a thin `fs.rs` that just holds the `CasFS`
struct and delegates. In the same PRD:

- Collapsed the two-shape `CasFS` (`new` + `new_multi_user` with
  optional fields) into one shape that always takes a
  `SharedBlockStore`. Single-namespace use is a convenience shim
  (`CasFS::single_namespace`).
- Replaced `PendingMarker` (counter + remember-to-call-the-right-
  method) with `BlockWriteGuard` (`#[must_use]` RAII, Drop reports
  dropped-on-pending).
- Moved `AsyncFileSystem` trait + `RealAsyncFs` into their own
  `async_fs.rs`.
- **Caught and fixed a latent bug** while collapsing: the old
  `MetaStore::delete_object` looked up blocks in its own store's
  `_BLOCKS` tree, but in multi-user deployments that tree was
  empty because blocks lived in the shared store. Signature now
  takes `&BlockTree` explicitly; delete_path.rs passes the shared
  one.

Success criteria: all sibling files under 400 lines (met), fs.rs
non-test under 250 (**not met** -- 327 lines of thin delegations +
canonicalization + multipart plumbing; all load-bearing, not
reducible without awkward helper fns). 15 cas-storage unit tests
+ 5 s3-cas integration tests pass, clippy clean.

### PRD-002 -- s3s upgrade + edition bump + TLS consolidation

- **Deliverable A** (s3s off async_trait): **superseded.** See
  ADR-005's second-look below. Short version: the fork plan can
  not deliver what it claimed because of dyn-compat constraints
  in s3s itself. The hand-rolled `Pin<Box<dyn Future>>` macros in
  `metric_fwd!` / `route_fwd!` are accepted as a known wart. The
  architectural fix would be to stop wrapping `s3s::S3`
  altogether (a new pending PRD, see below).
- **Deliverable B** (edition 2018 -> 2024): done. Minor cleanups
  along the way: `gen` is now a reserved keyword (rand 0.8
  callers use `r#gen`), `if let Some(ref foo) = foo` where foo is
  already a reference is outlawed, `let`-chains stable.
- **Deliverable C** (one TLS stack): effectively done by two
  earlier moves. `openssl` was evicted from the tree when we
  switched `rusoto_core` to its `rustls` feature; then PRD-003
  removed `rusoto_core` entirely, leaving only `hyper-rustls`
  transitively via `s3s` itself. Only remaining
  `openssl-`-prefixed crate in the tree is `openssl-probe`, which
  is pure Rust (a cert-path helper, no FFI).

### PRD-003 -- remove rusoto_core::ByteStream (done)

`rusoto_core` was only in the workspace because its `ByteStream`
type was the input shape of `CasFS::store_object`. Rusoto is
unmaintained (last release 2022). Replaced with a minimal
`cas_storage::AsyncByteStream` -- 25 lines, a pinned boxed
`Stream<Item = io::Result<Bytes>> + Send + 'static`. That's the
whole type.

Cargo.lock shrank by ~380 lines; several transitive crates
(hyper-tls, webpki, rustls-native-certs, aws-shape packages,
jsonwebtoken, ...) left the tree. `cas-storage` now has zero
transitive TLS dependencies -- it is truly protocol-agnostic.

## 4. What the ADRs mean, in practice

### ADR-002 -- OpenSSL -> rustls migration (partial, now effectively complete)

Was tracked as partial because `openssl` was still transitively
present via `rusoto_core`'s default features. After PRD-003
removed `rusoto_core` outright, the original migration intent is
satisfied. This ADR could be marked closed at the next doc pass;
it's just not been touched because no new work depends on it.

### ADR-004 -- drop async_trait where we own the trait

Owns-trait side of the house: done. `cas-storage` never had an
`async_trait` dependency after its sibling-module split. The
remaining `async_trait` usage in `s3-cas` comes from impls of
`s3s::S3` and `s3s::auth::S3Auth`, which are upstream-owned
traits. That side is ADR-005's territory.

### ADR-005 -- upgrade s3s off async_trait (accepted; blockade lifted)

This is the most important ADR in the recent history. It started
life as a prerequisite -- "don't add new S3-surface work until
s3s is on native AFIT". It was accepted on 2026-04-25 to execute
via a local fork of `Nugine/s3s`. Within hours, the second-look
addendum killed that plan.

The killer: s3s stores its handlers as `Arc<dyn S3>` and holds
`Box<dyn S3Auth>` / `Box<dyn S3Host>` / `Box<dyn S3Access>` /
`Box<dyn S3Route>` inside its service and router. Dyn dispatch
is architectural to s3s. Native `async fn` in trait is
**not dyn-compatible** on stable Rust (still experimental).
`#[async_trait]` exists precisely to desugar `async fn` methods
into `fn foo(...) -> Pin<Box<dyn Future>>`, which is dyn-safe.

So the three fork shapes reduce to:

1. Drop `#[async_trait]` naively -> breaks s3s itself.
2. Keep the Pin-Box signature hand-rolled in the fork's codegen
   template -> our macros still must emit `Pin<Box<Future>>` to
   match. Zero net win; we just move the hand-roll.
3. Restructure s3s to not use dyn -> upstream is moving in the
   opposite direction (added `S3ConfigProvider` in 0.14.0-dev),
   and the change leaks generics through the whole s3s public
   API. Not a tractable fork.

Decision: accept the hand-rolled macros as permanent, document
them, and lift the blockade. The `delandtj/s3s` fork created in
the first addendum stays as a vendoring parking spot, not a live
pin.

**What actually retires the macro wart** is architectural,
tracked as a pending candidate PRD in INDEX.md: "retire
MetricFs + S3UserRouter via 2a+2b". Two independent moves, either
of which kills one wrapper + one macro:

- **2a**: merge per-user routing into `S3FS` (`S3FS` learns to
  look up the per-user `CasFS` from `UserStore` based on the
  authenticated access key). Kills `S3UserRouter` and
  `route_fwd!`.
- **2b**: move `MetricFs` to a `tower::Service` layer in front
  of s3s. Kills `MetricFs` and `metric_fwd!`.

Neither touches `#[async_trait]` on s3s's traits; they sidestep
by not implementing those traits a second time.

### ADR-006 -- presigned URLs (Deliverable B shipped)

Presigned URLs were always free on the server side -- s3s
verifies SigV4 signatures the same way whether they arrive as an
`Authorization` header or as `X-Amz-*` query params. ADR-006's
Deliverable B was the CLI convenience:

```
s3-cas presign --meta-root ... --user alice \
    --endpoint http://host:8014 --ttl 15m bucket path/to/key
```

Reads the user's credentials from the local `_USERS` partition,
signs via `aws-sigv4` (already transitive), prints one URL to
stdout. TTL capped at 7 days per SigV4. 7 unit tests cover the
URL shape, determinism, TTL bounds, and method-affects-signature.

Server-side verification needed no code change.

### ADR-007 -- HTTP exposure options (option analysis, refined)

The question behind ADR-007: "Can a browser fetch
`http://host/bucket/dir/file.html` without an S3 client?"

Three lanes:

- **Option A** -- bucket-level `public_read` flag on `BucketMeta`.
  Anon GET/HEAD allowed when the flag is set. Does NOT give you
  index.html resolution or directory listings. Minimal.
- **Option B** -- S3-compatible static website hosting
  (`PutBucketWebsite` etc.). Heavy. Only worth it if a tool
  insists on AWS website semantics verbatim.
- **Option C** -- new `http-cas` crate, a first-party HTTP
  adapter that reads `cas-storage` directly. Does not touch
  `s3s::S3` at all. Browsable, cache-friendly, logical home for
  "drop this bucket behind nginx and forget about S3 clients".

Default recommendation for "host static assets built by CI":
A + C combined.

ADR-007 was originally written with ADR-005 as a prerequisite.
The 2026-04-25 refresh removed that gate, named the `S3Access`
hook as the preferred integration point for Option A (narrow
single-method trait, sidesteps the hand-rolled macro cost), and
promoted a handful of items from open-questions to decisions:

- Bucket names for public buckets are globally unique
  (first-come-first-served at flip time). User confirmed.
- 403 AccessDenied on all denied anon access, whether the bucket
  is missing or private (no bucket-existence enumeration via
  404-vs-403). User confirmed.
- What "public-read" covers: explicit anon-allowlist table;
  `ListObjects` is NOT in the default allowlist, gated on a
  separate opt-in `public_list` flag.
- Error model, ETag shape (MD5-hex quoted), schema migration
  plan (`Option<bool>` for the new field so bincode decodes of
  pre-migration records yield `None` == private).

**Outstanding ADR-007 tweak (not yet done):** the "vhost style
rejected" paragraph in the bucket-name-disambiguation decision
should be demoted back to "still open at PRD time". User did not
commit to rejecting it. The rest of that decision (path style
with global uniqueness) stands.

## 5. The architectural question behind the macro wart

Both `MetricFs` (metrics wrapper) and `S3UserRouter` (per-user
routing wrapper) wrap `s3s::S3`. Because s3s's `S3` trait is
`#[async_trait]`-annotated, and because `macro_rules!` inside an
`#[async_trait]`-annotated impl can't emit `async fn` methods
(attribute-macro expansion order produces E0195), the two
wrappers must hand-roll `Pin<Box<dyn Future<Output=...> + Send +
'async_trait>>` signatures from `macro_rules!`. That shape leaks
internals of what `async_trait v0.1.x` happens to expand to today;
it is not future-proof against a minor bump of the crate.

ADR-005 tried to fix this by upgrading s3s off async_trait.
ADR-005's second-look showed that was the wrong layer -- the
actual fix is to stop wrapping `s3s::S3` at all. A new PRD, not
yet written, would:

- Refactor `S3FS` to hold a `UserStore` directly and look up the
  per-user `CasFS` inside each method via the authenticated
  access key. No `S3UserRouter` wrapper needed.
- Move metrics to a `tower::Service` layer in front of s3s. No
  `MetricFs` wrapper needed.

That PRD is listed in INDEX.md's pending-candidate section as
"retire MetricFs + S3UserRouter via 2a+2b".

## 6. What is actively on the table

Not in a specific order; pick what the next session has appetite
for.

**Small, visible:**

- Mark ADR-002 closed (the openssl migration is effectively done
  now via PRD-003's eviction of rusoto; just update the status
  header).
- Finish the ADR-007 vhost demotion the user asked for.
- Wire benches into CI (benches are functional again after the
  2026-04-25 bench rescue; just not automated).

**New PRDs waiting to be written:**

- **HTTP exposure PRD** picking a lane from ADR-007. Default
  recommendation is A + C.
- **OpenRPC management interface PRD.** Surfaced in the
  2026-04-25 wind-down but not yet written. Would add a whole
  new RPC surface alongside S3, probably on its own port, with
  admin-scope auth separate from S3 user credentials. Likely
  leans on `hero_router` / `herolib_openrpc` from the user's
  toolchain.
- **Retire MetricFs + S3UserRouter** (the ADR-005 second-look
  closer, the real architectural fix for the hand-rolled macros).
- **Per-user metrics and quotas.** Previously blocked by
  ADR-005; now free to proceed. Shape depends partly on whether
  the retire-wrappers PRD lands first (if it does, metrics live
  at the middleware layer and "per-user metrics" is a label
  story; if not, it's inside the wrapper).

**Near-zero-effort hygiene:**

- Integration test for presign against an actual running server
  (current unit tests cover the URL shape; a real-HTTP-listener
  test would verify s3s's SigV4 validator accepts the URL before
  expiry and rejects after). Non-trivial scaffolding.

## 7. The feel of the project

Three recurring patterns that are worth knowing before making
changes:

1. **"Data leakage OK, data loss never."** The refcount invariant
   (`docs/arch/refcount.md`) accepts orphan blocks on failure and
   refuses orphan metadata. Any change to the write path must
   preserve this by structure, not by comment.
2. **"Short transactions, no .await."** The Fjall deadlock
   postmortem (`docs/arch/deadlock-fix.md`) produced the rule
   that metadata transactions hold write permits for microseconds
   only, with no filesystem I/O inside them. `write_path.rs`
   commits the metadata before any on-disk write and runs a
   compensating delete if the on-disk write fails. This is the
   single most subtle piece of the repo.
3. **"Number at write-time only."** PRDs and ADRs are numbered
   only when someone actually writes them. Unwritten work is
   referred to by description. Numbers are never pre-allocated
   and never renumbered. This is why there is no PRD-004 yet
   even though several candidates are queued.

## 8. What to avoid

- Adding a new wrapper around `s3s::S3` unless you have a
  strategy for the hand-rolled `Pin<Box<Future>>` macros. See
  ADR-005's second-look.
- Bumping `s3s` past v0.11.1 without first checking whether it
  has dropped `#[async_trait]` from its `S3`/`S3Auth` traits. It
  has not as of 0.14.0-dev; check at bump time.
- Changing `BucketMeta`'s bincode layout without a schema-tag
  strategy. Existing deployments have records in this shape.
- Touching `cas/write_path.rs` without understanding the commit-
  before-write discipline. The deadlock postmortem exists for a
  reason.
